# امنیت

## ۱) جداسازی مستأجر (Tenant isolation)

- ستون `org_id` روی همه‌ی جدول‌های دامنه + **RLS اجباری** روی ۱۷ جدول حساس.
- اپلیکیشن با نقش **غیرسوپریوزر** `openbot_app` وصل می‌شود؛ اگر با سوپریوزر وصل شود
  RLS دور زده می‌شود و این یک قاعده‌ی عملیاتی حیاتی است.
- سیاست: `app.org_id` (تنظیم در هر تراکنش) یا `app.bypass_rls='on'` (فقط jobهای سیستمی).
- نبودِ context ⇒ **صفر ردیف**. (تست `tests/test_rls.py`)

```python
async with session_scope(org_id=org.id) as db:      # تنظیم app.org_id
    ...
```

**نکته‌ی پیاده‌سازی که در عمل باگ شد:** `SET LOCAL` به تراکنش بسته است و با هر `commit`
پاک می‌شود؛ موتور اجرا پس از هر commit دوباره تنانت را bind می‌کند.

## ۲) احراز هویت و نشست

| مورد | پیاده‌سازی |
|---|---|
| رمز | Argon2id (`argon2-cffi`)، rehash خودکار در ورود |
| توکن دسترسی | JWT HS256، ۱۵ دقیقه |
| توکن refresh | ۷ روز، **یک‌بارمصرف** (hash در `sessions`، چرخش در هر استفاده) |
| توکن دستگاه | JWT با `kind=device`، مخصوص کانکتور |
| مرورگر | توکن در کوکی httpOnly سمت Next؛ هیچ توکنی در localStorage نهایی نیست (قدم ۷) |
| ثبت تلاش ورود | `login_attempts` (موفق و ناموفق) |
| 2FA | جدول `user_mfa` آماده، TOTP پیاده‌سازی نشده (roadmap) |

## ۳) رمزنگاری داده

| داده | روش |
|---|---|
| کلید پروایدر، کلید ابزار، توکن MCP، راز MFA | AES‑256‑GCM با `APP_MASTER_KEY` |
| AAD | `provider:{slug}` / `tool:{slug}` / `mcp:{server_id}` → جابجایی ciphertext بین رکوردها بی‌اثر است |
| نمایش | همیشه ماسک (`sk-f…3456`)؛ کلید خام هرگز در پاسخ API نیست |
| لاگ خطا | `scrub()` کلید را از پیام خطای پروایدر حذف می‌کند |

## ۴) دسترسی نقش‌محور (RBAC)

دو نقش داریم، نه بیشتر:

| نقش | کیست | می‌تواند |
|---|---|---|
| `admin` | کارمند پلتفرم (ایمیل + رمز) | پروایدر، مدل، قیمت، کاربران، حسابداری، مشاهدهٔ هزینهٔ دلاری |
| `user` | مشتری (فقط OTP موبایل) | کیف پول خودش، ساخت ایجنت/ابزار/کانال/اپ، اجرای ایجنت، کاتالوگ |

قاعده‌ها:

- مسیرهای ادمین با `require_admin` بسته شده‌اند: `/v1/providers`، `/v1/models` (لیست،
  جزئیات، تاریخچهٔ قیمت)، `/v1/users`، `/v1/payments`، `/v1/billing/*`.
- مشتری روی منابع خودش کار می‌کند: هر رکورد با `org_id` و `owns_or_admin` بررسی می‌شود؛
  کیف پول فقط `user_id` خودش را می‌بیند.
- `/v1/catalog/models` تنها راه دیدن مدل برای مشتری است و **نام فارسی + قیمت تومانی**
  می‌دهد؛ `provider_id`، `base_url`، قیمت دلاری، `price_source` و `markup_percent` در
  پاسخ نیست. `cost_usd` در پاسخ اجراها هم برای مشتری `null` می‌شود.
- ابزار/پرامپت **سراسری** برای همه فقط‌خواندنی است.
- نقش در سطح دیتابیس هم اجبار می‌شود: `ck_users_role CHECK (role IN ('admin','user'))`
  (مایگریشن `0016`). و چون `users` **FORCE RLS** دارد، هر اصلاح نقش باید با
  `app.bypass_rls='on'` (یا `python -m app.cli promote-admin`) انجام شود؛ وگرنه `UPDATE`
  صفر ردیف را عوض می‌کند و «موفق» گزارش می‌شود — همان چیزی که یک‌بار ادمین را از پنل
  بیرون انداخت.

## ۵) تأیید انسانی (Human-in-the-loop)

- ماتریس ریسک در [tool-contract.md](tool-contract.md) — بخش «سیاست اجرا».
- ابزار `high` هرگز بدون تأیید اجرا نمی‌شود، حتی با permission=`auto`.
- اجرا در `runs.state.pending` **ذخیره** می‌شود (قابل ادامه بعد از ری‌استارت).
- هر تأیید با `tool_invocations.approved_by` ثبت می‌شود.

## ۶) کانکتور (دسترسی به ماشین)

| تهدید | کنترل |
|---|---|
| نفوذ به دستگاه از اینترنت | کانکتور **فقط خروجی** وصل می‌شود؛ هیچ پورت ورودی باز نیست |
| سرقت کد جفت‌سازی | کد یک‌بارمصرف، ۸ کاراکتر، ۱۰ دقیقه اعتبار، چرخش با دکمه |
| سرقت توکن | توکن کوتاه‌عمر مخصوص دستگاه؛ غیرفعال‌سازی دستگاه = `close(4403)` |
| نوشتن/خواندن خارج از محدوده | `allowed_paths` در **سرور و کانکتور** بررسی می‌شود |
| اجرای فرمان دلخواه | `shell.run` فقط با پیشوندهای مجاز (`--allow-cmd`) |
| خطای بی‌صدا | هر اجرا با args/result/status در `tool_invocations` |
| چند ابزار همزمان | هر فراخوانی `call_id` مستقل + timeout (پیش‌فرض ۶۰s) |

**شکاف باقی‌مانده:** امضای Ed25519 هر پیام اعتبارسنجی نمی‌شود (کلید عمومی ذخیره می‌شود).

## ۷) امنیت خروجی به اینترنت

- همه‌ی کلاینت‌ها `trust_env=False` → پروکسی سیستمی هرگز ترافیک مدل را نمی‌دزدد.
- پروکسی فقط به‌صورت **صریح** با `meta.proxy` روی هر پروایدر.
- ابزار HTTP: `allowed_domains` اجباری + متد محدود + هدر ASCII.
- بیلتین `http.request`: همان allowlist، بدون کلید.

## ۸) درگاه پرداخت

پورت `PaymentGateway` با دو پیاده‌سازی: `NoopGateway` (پیش‌فرض، همه‌چیز ۴۰۹/۵۰۳) و
`zarinpal` (واقعی). تا وقتی `APP_PAYMENT_GATEWAY=noop` باشد هیچ داده‌ی پرداختی در
سیستم نیست.

کنترل‌های زرین‌پال:

| تهدید | کنترل |
|---|---|
| بازپرداخت/تأیید جعلی callback | `verify` سمت سرور با `authority` + `amount`؛ مبلغ از رکورد ما خوانده می‌شود نه از کوئری |
| دو بار شارژ با یک پرداخت | ردیف پرداخت قبل از ریدایرکت ساخته می‌شود؛ `apply_callback` با `FOR UPDATE` روی `payer`، `paid` را زودتر برمی‌گرداند، کد `101` (already verified) هم پذیرفته می‌شود |
| گم‌شدن callback | `POST /v1/payments/{id}/verify` ادمین، همان تابع idempotent را دوباره اجرا می‌کند |
| نشت بین مستأجرها | `payments` زیر RLS؛ callback با `set_bypass_rls` پیدا می‌کند و بعد `set_tenant` می‌بندد |
| ثبت کارت در سیستم | هیچ داده‌ی کارتی ذخیره نمی‌شود (فقط `authority`/`ref_id`) |

تنظیمات لازم: `APP_PAYMENT_GATEWAY=zarinpal`، `APP_ZARINPAL_MERCHANT_ID`،
`APP_PAYMENT_CALLBACK_URL` (باید عمومی و https باشد)، `APP_ZARINPAL_SANDBOX=false`.

## ۹) حسابرسی و نگهداشت

- `usage_ledger` و `price_history` فقط append.
- لاگ ساختار‌یافته JSON با `request_id` روی هر درخواست.
- نگهداشت پیشنهادی در [data-model.md](data-model.md) — بخش «نگهداشت پیشنهادی».
